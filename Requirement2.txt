Enhance the existing API testing web application by adding a **Database Integration and Dynamic Test Data** feature.

The goal is to allow users to connect to a database, execute SQL queries, retrieve values, and automatically use those values inside API requests.

The application should work like:

```text
Database
   ↓
SQL Query
   ↓
Query Result
   ↓
Map Database Columns to Variables
   ↓
API Request JSON
   ↓
Send API
   ↓
API Response
```

Do NOT redesign or replace the existing API testing functionality. Add this as a new integrated feature while keeping the current UI and workflow intact.

# 2. Database Connection Manager

# 3. Security

Database credentials must NEVER be exposed in the browser frontend.

Use a backend service for database communication.

Architecture:

```text
Web UI
   ↓
Backend API
   ↓
Database
```

The frontend should never directly establish database connections.

Passwords and sensitive connection details should be encrypted or securely stored.

Never display passwords in logs.

Never send database credentials to the target API.

# 6. Database Variables

This is the most important feature.

Allow users to convert database query results into variables.

For example, query:

```sql
SELECT
    CUSTOMER_ID,
    CUSTOMER_NAME,
    EMAIL
FROM CUSTOMER
WHERE STATUS = 'ACTIVE'
FETCH FIRST 1 ROW ONLY
```

returns:

```json
{
  "CUSTOMER_ID": 10001,
  "CUSTOMER_NAME": "John",
  "EMAIL": "john@test.com"
}
```

Automatically expose variables:

```text
{{db.CUSTOMER_ID}}
{{db.CUSTOMER_NAME}}
{{db.EMAIL}}
```

# 7. Use Database Values in API Request

Allow database variables to be used anywhere in an API request.

Example URL:

```text
https://api.example.com/customer/{{db.CUSTOMER_ID}}
```

Example query parameter:

```text
customerId = {{db.CUSTOMER_ID}}
```

Example header:

```text
X-Customer-ID = {{db.CUSTOMER_ID}}
```

Example JSON body:

```json
{
  "customerId": "{{db.CUSTOMER_ID}}",
  "customerName": "{{db.CUSTOMER_NAME}}",
  "email": "{{db.EMAIL}}"
}
```

Before sending the API request, resolve the variables.

Display a preview:

```text
Template:

{
  "customerId": "{{db.CUSTOMER_ID}}",
  "email": "{{db.EMAIL}}"
}

Resolved:

{
  "customerId": "10001",
  "email": "john@test.com"
}
```

Provide:

```text
[Show Resolved Request]
```

# 23. Example End-to-End Scenario

The application should support this complete workflow:

### Step 1 – Query Database

```sql
SELECT
    CUSTOMER_ID,
    CUSTOMER_NAME,
    EMAIL
FROM CUSTOMER
WHERE STATUS = 'ACTIVE'
FETCH FIRST 1 ROW ONLY
```

### Step 2 – Result

```json
{
  "CUSTOMER_ID": 10001,
  "CUSTOMER_NAME": "John",
  "EMAIL": "john@test.com"
}
```

### Step 3 – Variables

Automatically create:

```text
{{db.CUSTOMER_ID}}
{{db.CUSTOMER_NAME}}
{{db.EMAIL}}
```

### Step 4 – API Request

```text
POST https://api.example.com/customer
```

Body:

```json
{
  "customerId": "{{db.CUSTOMER_ID}}",
  "name": "{{db.CUSTOMER_NAME}}",
  "email": "{{db.EMAIL}}"
}
```

### Step 5 – Resolve

```json
{
  "customerId": "10001",
  "name": "John",
  "email": "john@test.com"
}
```

### Step 6 – Send API

Execute the API request.

### Step 7 – Validate Response

Compare API response against database values.

```text
✓ Customer ID matches
✓ Customer name matches
✓ Email matches
✓ API status = 200
```

# 24. Important Implementation Requirement

Build this as a **fully functional feature**, not just a visual mockup.

Start with:

1. Database connection management
2. PostgreSQL + MySQL + Oracle support
3. Secure backend database connectivity
4. SQL editor
5. Execute SQL
6. Display query results
7. Convert result columns into variables
8. Use variables inside API URL/body/headers/params
9. Database → API workflow
10. API → Database validation
11. Multiple-row data-driven execution
12. Query history
13. Saved queries
14. Environment-specific database connections

Keep the existing API testing functionality working exactly as it does today.

The final application should become a lightweight **API + Database Testing platform**, allowing QA engineers to perform:

```text
Database Setup
      ↓
Fetch Test Data
      ↓
API Request
      ↓
API Response
      ↓
Database Validation
      ↓
Test Result
```

The architecture should be extensible so that additional databases, advanced assertions, test suites, scheduled execution, and CI/CD integration can be added later.
